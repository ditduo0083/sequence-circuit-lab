# 회로해석 콘텐츠 쓰기 (동작 설명 · 접점 고르기)

회로해석은 시뮬레이션을 본 학생이 **직접 해 보는 실습**이다(D0010). 한 페이지에 탭 세 개: ① 동작 보기(기기 찾기 + '시뮬레이션 열기') ② 동작 설명 쓰기 ③ 접점 고르기. 이 스킬은 ②의 모범 답안과 ③의 문제를 쓰는 규칙이다. 화면·채점 코드는 공용 엔진이 하므로 **데이터 두 필드만** 쓴다.

> 엔진(열지 않음): `핀번호_작업/v2_엔진분리/공용/interpret-engine.js`·`interpret-page.css`, 이력 `공용/ENGINE_CHANGELOG.md`. 견본: `회로/circuit-001.js`(전기), `circuit-e01.js`(승강기).

## 0. 절대 규칙

- **공단 문장을 베끼지 않는다.** 모범 답안·문제·해설은 회로 동작을 이해한 뒤 자기 말로 쓴다. 원문 PDF·이미지는 저장소에 넣지 않는다(설계 결정 3).
- **원문 대조를 반드시 돌린다**(C001 방식): 공백·기호를 뺀 글자열에서 원문과 **가장 길게 그대로 겹치는 부분** 글자 수. 기준 **15자 미만**. 지금까지 결과: 전기 001 11자, 002~018 4~9자, 승강기 4~6자. 원문 = 같은 번호 PDF 7·8쪽(전기), 7쪽(승강기) `pdftotext` 추출문. 추출문·PDF 는 시스템 임시 폴더에서만 쓰고 저장소·scratch 에 남기지 않는다. 대조 결과를 통과하면 `synopsis.verified: true` — `false` 인 동안 학생 화면에 모범 답안이 숨는다.
- **서술형은 자동 채점하지 않는다**(설계 결정 15, D0008). 제출은 핀번호와 같은 **PNG**(이름·학번·날짜 포함). AI 유사도·키워드 채점을 넣지 않는다. 선생님이 직접 판단한다.
- 회로 데이터의 다른 필드(`layout`, `answerKey`, `devices`, `items` 좌표·순서)는 **건드리지 않는다.** 이 스킬로 바꾸는 것은 `synopsis`·`interpretQuestions` 둘뿐이다.
- 문서는 한국어. 커밋은 바꾼 파일만 `git add <경로>`. 배포는 따로 한다.

## 1. 전기와 승강기의 차이 (혼동 금지)

- **전기기능사 001~018**: 원본 PDF 8쪽에 공식 "제어회로의 동작 사항" 서술이 있다. 원문 대조가 "베끼지 않았는지"를 실제로 검증한다. 논리 기준은 회로 앱의 동작 모델(`circuit-model.js`)과 도면.
- **승강기기능사 e01~e10**: 공식 동작 서술 페이지가 **없다**(5쪽은 회로도·기구명뿐). 모범 답안은 **도면을 직접 판독해 새로 쓴 해석**이다. 원문 대조 4~6자는 우연한 겹침 확인일 뿐이고 공식 서술과의 논리 일치 검증이 아니다. 신뢰도는 회로 논리 검사(`검사하기.cjs`)와 시뮬레이션 모델 시험까지만 기계적으로 보장된다 → 판독 근거(어느 접점이 어느 코일을 끊는지)를 보고서에 적고, 시뮬레이션(`/e/NN/sim/`)과 대조한다. 사례: e03 은 "번갈아 반복"이 아니라 "정·역 한 번씩 뒤 정지"였다(0025 발견 → 0026 수정).

## 2. `synopsis` (동작 설명 모범 답안)

```js
synopsis: {
  text: '문장. ' + '문장. ' + …,   // 한 문장 = 한 사건(입력 → 접점 → 코일 → 부하)
  verified: true                  // 원문 대조 통과 뒤에만
}
```

- 순서: 전원 투입 → (자동/수동 선택) → 기동 → 자기유지 → 타이머·플리커 → 정지 → 과부하(EOCR) 트립·경보 → 리셋. 회로에 없는 기능은 쓰지 않는다.
- 문장마다 **원인(누른 것·닫힌 접점) → 결과(여자된 코일 → 운전·점등)** 를 한 번에. 기구 이름은 도면 태그 그대로(MC1, T, FR, X, PB0 …). a/b, 순시/한시를 분명히.
- 문장 수는 8~12개 정도. B안 비교 화면(요청 0059)이 **문장마다 '내 설명에도 있어요' 체크**를 붙이므로, 한 문장에 사건을 두세 개 섞지 않는다(체크가 애매해진다). 문장 끝은 `. ` 로 끊는다.

## 3. `interpretQuestions` (접점 고르기, 회로당 9개)

```js
{ id: 'q1', prompt: '…은?', answerItemIds: ['flsContact'], multi: false, explain: '…해요.' }
```

- `id` 는 `q1`~`q9`. `answerItemIds` 는 **`layout.items` 에 이미 있고 회로도에 기호가 그려지는 id** 만(접점 id, 코일·램프 `coil-태그`). 주회로 극·FLS 전극은 고를 수 없다. 새 id 를 만들지 않는다.
- `multi: false` → 하나 누르면 바로 판정, `answerItemIds` 가 여러 개면 **그중 아무거나 하나**가 정답. `multi: true` → 여러 개 고른 뒤 '확인', `answerItemIds` 를 **빠짐없이, 더도 덜도 없이** 골라야 정답.
- 고루 섞는다: 기동 접점, 자기유지, 인터록, 순시 vs 한시(삼각형 표시), 플리커, 정지(b접점), EOCR 트립(b 열림 / a 닫힘), 경보. 한 기구에 문제가 몰리지 않게.
- `prompt` 는 상황 + 묻는 것(접점인지 코일인지). `explain` 은 학생 말투 한두 문장(“~해요”), 회로도에서 어디를 보면 되는지 힌트(“맨 위 가로줄의”, “삼각형 표시가 있는”).
- 정답이 도면상 둘 이상일 수 있으면(어느 것을 골라도 맞음) 둘 다 넣고 `multi: false`, '모두 고르세요'면 `multi: true`. 애매하면 질문을 좁힌다.

## 4. 확인

1. `node 핀번호_작업/v2_엔진분리/검사/검사하기.cjs NNN` — 회로 데이터 오류·경고 0(다른 필드를 안 건드렸는지). **문항 검사는 이 도구가 하지 않는다** — 회로해석 엔진이 페이지를 열 때 `answerItemIds` 없음·그려지지 않는 id 를 화면 위 경고로 낸다. 그래서 3번 브라우저 확인에서 경고 상자가 없는지 꼭 본다(`synopsis.verified` 가 `true` 가 아니어도 경고).
2. 원문 대조 — 문장·문제·해설 **전부**를 대상으로 최장 연속 일치 글자 수를 표로(회로별 최댓값).
3. 브라우저: `/c/NNN/interpret/`(또는 `v2_엔진분리/회로/interpret.html` 파일 열기)에서 ② 쓰기 → '다 썼어요 → 모범 답안과 나란히 비교' → 체크 → PNG 저장, ③ 9문제 풀기. 콘솔 오류 0, 1366·390px 가로 넘침 없음.
4. 승강기는 시뮬레이션에서 문장마다 그 사건을 재현해 본다.
5. 보고서에 회로별 표(요점 · 문장 수 · 문제 수 · 원문 최장 일치 · 검사)와 판독이 애매한 곳을 적는다.

## 5. 하지 않는 것

- 엔진·CSS 수정(화면 배치 B안, 비교 화면, 도움말은 엔진이 한다). 필요하면 요청으로.
- 자동 채점·점수화, 텍스트 업로드, 서버 저장.
- 모범 답안을 '정답'이라고 부르지 않는다 — 화면 말은 '모범 답안', 스스로 확인은 '점수 아님'.
